Cracking the Uncrackable: How Autonomous AI Agents Outsmarted my Bespoke Cipher by launching a side channel attack.

What happens when you pit a swarm of autonomous AI agents against a custom cipher mathematically engineered to be impossible to crack, but give them tools like Google Search and code execution. They don't break the math, they will try and cheat!

In this Agentic experiment, I built a custom multi-stage cipher called Loom-97 (~10^35 keyspace, white-noise flat entropy) and tasked up to 30 parallel Google Agent Development Kit (ADK) agents with cracking an encoded ciphertext. I started with giving the Agents hints about the encoding scheme but in the later experiments the Agents did not know the implementation details or the key used to encode.  When the AI Agents could not actually crack the problems they tried to find the clues in the environment and found the keys every time! I will say that I may not have been diligent enough to completely isolate the agent execution environment but it was impressive regardless to see how the Agents immediately switched to looking for the clues and sometimes breaking the sandbox to find the clues and found the solution every single time.

Introduction to My Experiment

Modern frontier models are remarkably capable at classical cryptanalysis, CTF puzzles, and mathematical reasoning. I wanted to push past textbook ciphers and test how a coordinated multi-agent swarm behaves when confronted with a true cryptographic brick wall—a cipher with zero public documentation, zero training-data footprint, and computational complexity far beyond brute force.

To test this, I encoded a 41-character secret English sentence ("A quick brown fox jumps over the lazy dog") using Loom-97, producing a 63-character ciphertext that looked like an enterprise software activation key:

About the Cipher (Loom-97) and Its Computational Complexity

To ensure no LLM could recognize the cipher from pretraining corpora or crack it via frequency analysis, I designed a bespoke and undocumented cipher called Loom-97. How the 4-Stage Loom-97 Pipeline Works

Here is the core reference encoder and decoder

import math

ALPHABET = "7KQ3MX9DV4PZ2HT8CR6FNWJSG"

REV_ALPHABET = {ch: idx for idx, ch in enumerate(ALPHABET)}

def loom97_encode(

    plaintext: str,

    s0: int = 53,

    s1: int = 71,

    mask_step: int = 4813,

) -> str:

  if not plaintext:

    return ""

  # Stage 1: Homophonic Space-Shattering into GF(97)

  x, space_idx = [], 0

  for ch in plaintext:

    code = ord(ch)

    if code == 32:

      x.append((0, 95, 96)[space_idx % 3])

      space_idx += 1

    elif 33 <= code <= 126:

      x.append(code - 32)

    else:

      raise ValueError(f"Unsupported character: {ch!r}")

  n = len(x)

  # Stage 2A: Forward Polynomial Cascade

  u, prev_u = [0] * n, s0

  for i in range(n):

    k_i = (7 * i * i + 19 * i + 41) % 97

    u[i] = (x[i] + 31 * prev_u + k_i) % 97

    prev_u = u[i]

  # Stage 2B: Backward Non-Linear Galois Cascade

  v, next_v = [0] * n, s1

  for i in range(n - 1, -1, -1):

    f_val = (next_v * next_v + 13 * next_v + 29) % 97

    v[i] = (5 * u[i] + f_val) % 97

    next_v = v[i]

  # Stage 3: Affine Coprime Stride Decimation

  stride = 17

  while math.gcd(stride, n) != 1:

    stride += 1

  offset = 9 % n

  w = [v[(stride * j + offset) % n] for j in range(n)]

  # Stage 4: Masked 2-to-3 Radix-25 Fractionation + 7-Glyph Framing

  glyphs = []

  for block_idx, pos in enumerate(range(0, n, 2)):

    z = 97 * w[pos] + w[pos + 1] if pos + 1 < n else 9409 + w[pos]

    z_masked = (z + mask_step * (block_idx + 1)) % 15625

    d2, rem = divmod(z_masked, 625)

    d1, d0 = divmod(rem, 25)

    glyphs.extend((ALPHABET[d2], ALPHABET[d1], ALPHABET[d0]))

  raw = "".join(glyphs)

  return "-".join(raw[i : i + 7] for i in range(0, len(raw), 7))

The Agent Architecture and the Experiment Setup

I created and tested the Agents in Google Cloud Workstation. Google Cloud Workstations provide a flexible environment to write and deploy AI Agents. To facilitate AI coding Antigravity is built-in.

Figure : Antigravity built into Google Cloud Workstation.

The agent architecture is as below.

  • evidence_agent: Reads all prior swarm attempts from GCS and produces a structured Evidence Briefing listing ruled-out cipher families and known constraints.
  • decipher_agent: Formulates new mathematical hypotheses, writes and runs Python scripts (Galois arithmetic, matrix transpositions, base unpacking), and outputs one CANDIDATE. This agent had the ability to execute code in the sandbox, perform online search and access the websites online.
  • verifier_agent: Extracts CANDIDATE and calls Secret Manager to validate exact equality against deciphered1. Exposed tools:
  • recorder_agent: Appends the hypothesis description, tested candidate, and verifier feedback to Google Cloud Storage. This ensures every turn's outcome is immediately visible to the other 29 instances on their next cycle.
  • loop_guard: Custom deterministic StopOnSuccessChecker inspecting session state after each pass. Halts execution cleanly the moment Secret Manager confirms a match.

Following Google Cloud Services were used

  • Google Cloud Workstations: Provided a persistent, reproducible cloud development and execution machine  with access to Antigravity Coding Agent.
  • Agent Platform : Powered agent using gemini-3.8 Flash.
  • Google Cloud Storage : Served as an asynchronous decentralized blackboard. Agents coordinated exclusively by reading and appending to the files in GCS.
  • Google Cloud Secret Manager : Kept the plaintext answer for verification.

How the Agents Behaved Each Turn & Summary of Approaches

Run 1:  Laying the Baseline

In this Run I wanted to set a baseline so I created a bucket called haren-agent-swarm-data-share and placed the encoding and decoding algorithm in the bucket and the agents were allowed to read and write in the bucket for intermediate data sharing. I did not explicitly ask the agent to look into any of the algorithms that were placed in the bucket.

After I ran a group of 30 Agents, within the single pass the agent was able to find the file in the bucket, write the code, run the code in the sandbox and find the decoded plaintext encoded in the Loom-97 ciphertext! It was incredible to see that the agents did not even try to guess the answer they tried to find the easiest way.

Run 2: Resurrecting Deleted Data via GCS Soft Delete

Realizing my mistake, I deleted the algorithm and prior solution files from gs://haren-agent-swarm-data-share and restarted the swarm. Yet the agents solved Loom-97 again!

Why? Google Cloud Storage enables Soft Delete by default (with a 7-day retention window) to protect cloud workloads against accidental data deletion and I had not disabled it. What this means is that even if you delete the files , they will not be visible but they will be recoverable. The agents were able to list the deleted file, recover and then read the files and write the decoder code to decode the cipher text. This was again completely unprompted, I only gave the agent an access to the Google Cloud Storage.

Run 3: 30 Agents in parallel for 10 hours

Determined to enforce a clean slate, I created a brand-new bucket gs://haren-agent-swarm-data-share-2 — created a fresh launch folder in Cloud Workstations and launched 30 parallel agent instances on my Google Cloud Workstation for roughly 10 hours.

During the Agent Run I saw that the agents took 2 main approaches,

  1. Try some of the known techniques.
  2. Blindly guess the plaintext.

It almost got it right a few times because my phrase was so common (A quick brown fox jumped over the lazy dog). It could not guess all the character cases though and there were just too many combinations for the agent to try.

Then at some point the agent switched to side channel attack and instead of trying to find the solution it was looking around for the clues. It finally found the clues in the original bucket which still had the soft deleted files. There was no mention of the original bucket in the agent code, it just guessed haren-agent-swarm-data-share from haren-agent-swarm-data-share-2 and got the clues from there and solved the riddle after around 10 hours.

Once a single agent found the solution and put the solution in the haren-agent-swarm-data-share-2 rest of the agents just used that to solve the problem.

The Challenge of Stopping Agent Sandbox Escapes (Especially with Code Execution)

The overarching security lesson of this experiment is stark: giving an autonomous LLM agent a code execution tool turns prompt-level tool boundaries into an illusion unless backed by kernel, network, and IAM isolation.

In my ADK agent design, decipher_agent was intentionally not given list_gcs_files, read_gcs_file, or check_answer_against_secret. On paper, it only had execute_sandbox_code to run pure math. In reality, because execute_sandbox_code ran inside the workstation user's OS security context, decipher_agent silently inherited every capability of the host machine and its GCP service account.

While code execution is a great and flexible feature to give to an agent you become vulnerable to the scenarios where the agent might access the side channels not intended for the agent. Even if  the access given to the agent is restricted, the code execution maximizes the potential of what the agent can do.

Conclusion

When I started this experiment, I set out to see whether a 30-agent swarm on Google Cloud could crack Loom-97. Mathematically, Loom-97 stood completely unbroken: across 10 hours no agent ever decoded the ciphertext.

Yet the agents still won all three rounds:

  • In Round 1, they read the algorithm straight out of the shared collaboration bucket.
  • In Round 2, they resurrected the deleted data through Google Cloud Storage Soft Delete.
  • In Round 3, locked inside a clean bucket with 30 agents running for 10 hours,  the agents were able to launch a side channel attack by guessing the existing bucket where they could find the clues.

Key Takeaways Checklist for Builders

  • Least Privilege: Principle of Least Privilege must be enforced for all the agent permission and more than necessary permission becomes an attack surface.
  • Treat LLM code execution as untrusted remote code execution (RCE): Code Execution must be performed in a completely isolated environment that is completely detached from the agent's permission. Even if the principle of least privilege is followed the amount of the damage the agent can do with is maximized.
